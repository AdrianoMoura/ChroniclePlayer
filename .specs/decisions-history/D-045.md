# D-045

**Spec:** `authentication.md`

**Embedded-player session = Electron's ordinary unnamed default session (no custom `webPreferences.partition` anywhere), shared by the main window (and therefore the player's plain `<iframe>`, which always inherits its embedding page's session) and a new "Sign in to YouTube" action** (`bugs.md` [[B-093]]) — chosen over per-cookie injection between two separate sessions. Chronicle's own OAuth connect flow (D-001/D-012) always ran in the *system* browser, never touching Electron's own browsing session at all, which is why the embedded player's session started out never authenticated to Google — the previously-found workaround (clicking the iframe's own "Watch on YouTube" corner link, which opens a same-session popup window by default Electron behavior, signing in there) already proved a *shared* session is sufficient once actually signed into; the gap was only that this path had no deliberate, discoverable trigger. Settings → Connection gained a plain "Sign in to YouTube" button that opens a window at youtube.com in that same default session — no automation, no scraping, no cookie extraction (`youtube-api.md` §Terms-of-service constraints): the user signs in themselves, exactly like the corner-icon workaround, just reachable on purpose. **Revised same day**: first implemented as an explicitly *named* persistent partition instead of the default session, on the theory that naming it made the sharing more intentional/documented — this broke every thumbnail in the app, since `protocol.handle()` (`thumb://`) registers on `session.defaultSession` specifically and a custom partition is a different session with no handler on it. Reverted to the default session everywhere; no functional loss, since the default session was already what every window/iframe here implicitly shared before B-093 touched any of this. **Exercised 2026-07-15**, per the product owner's direction; needs the owner's own live validation (open the sign-in window, confirm authenticated state persists into the player) before considering the underlying bot-check symptom actually resolved.
