# D-048

**Spec:** `youtube-api.md`

**Removed the "channel unavailable" state entirely — an RSS 404 is just an ordinary per-channel failure now (retried next cycle), never a permanent, un-retried "channel deleted" verdict** (`bugs.md` [[B-110]]) — supersedes `youtube-api.md`'s original "Channel deleted/terminated" failure-handling row (mark `unavailable`, stop polling, show in a settings list). That row was never an actual product decision — it was an assumption baked in during earlier development with no owner sign-off and no corresponding `decisions.md` entry, surfaced now because it caused a real, silent bug: a single transient RSS 404 (YouTube's RSS edge can 404 for reasons that have nothing to do with the channel actually being gone) permanently excluded a channel from `listSubscribedChannels` — and therefore from every future routine sync **and** from the on-demand scroll-triggered archive backfill, since both read from the same query — with no retry, and no self-healing path, since the very query that would have reset the flag on a later successful check never ran again once excluded. The promised "settings list" surfacing this state was also never built, so the whole thing was invisible: a channel just silently stopped updating forever. **Superseding rationale (the product owner's own framing, 2026-07-16):** Chronicle's experience should work like YouTube's own pagination/discovery — keep trying to fetch content until a result genuinely comes back empty, that's how you know you've reached the end; a single failed attempt is never proof of anything permanent, and RSS calls cost no quota, so there's no efficiency reason to ever stop asking. **Exercised 2026-07-16:** the `'channel-unavailable'` domain error kind, `channelUnavailable()`, `markChannelUnavailable()`, and the `available` column/filter (`channels.available`, migrated away in schema v8) are all removed outright rather than left dormant; `rss-client.ts`'s 404 branch now falls through to the same `internal(...)` failure every other non-2xx RSS response already threw, which `discoverChannel`'s existing generic per-channel failure handling (log + retry next cycle) already covered before this change — no new retry mechanism was needed, only removing the special case that pre-empted it.
