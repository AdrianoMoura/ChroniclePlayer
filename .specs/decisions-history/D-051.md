# D-051

**Spec:** `playback.md`

**Closing the window to the tray (D-050's backgroundMode) with a video still playing no longer leaves it running silently and unreachable — it pops out to the always-on-top extract window instead (same mechanism as pressing `p`), or pauses, per a new Settings toggle.** A direct product-owner request, fully specified by the owner themselves, prompted by a real bug they hit live: closing the app window while tray mode was on didn't stop playback (it just hides the window, D-050) — audio kept playing with no visible player and no obvious way to stop it short of reopening from the tray. New `SettingsDto.popOutOnClose` (default **true**, only meaningful when `backgroundMode` is on — same conditional-visibility pattern as `startMinimized`): when true, closing the window while `PlayerSurfaceHandle.isStillGoing()` pops the current video into the extract window exactly like manual extraction, so it stays audible/visible and closing *that* window is what actually stops it; when false, closing pauses the video in place (`PlayerSurfaceHandle.pause()`, a new handle method issuing `command('pauseVideo')`) instead of popping out. **One behavioral difference from manual extraction, and the reason a plain reuse of the existing extract path wasn't enough:** normally closing the extract window restores the video docked into the main window (`player:restoreFromExtract`) — correct for the manual `p` case, but wrong here, since the main window is still hidden behind the tray at that point and restoring into it would silently resume the exact bug this decision fixes. `extractPlayer` (`ChronicleApi`, `IpcChannel.extractPlayer`) gained a fifth parameter, `auto: boolean`, set true only for this close-triggered path; `createExtractWindow` (`main.ts`) closes over it and skips the `player:restoreFromExtract` broadcast when `auto` is true, so the video simply stops for good instead of resurfacing. The main process doesn't own playback state, so it doesn't decide extract-vs-pause itself: the window's `close` handler (already intercepting close to hide instead of quit, per D-050) broadcasts a new `app:closedToTray` event; the renderer, which already holds `playerStack`/`settings` and the live `playerSurfaceRef`, makes the actual decision (`App.tsx`'s `handleClosedToTray`) — consistent with how every other player-state decision in the app already works. **Regression found live the same session, fixed immediately:** the owner's own manual test right after this landed found the on-screen Extract button (`PlayerDetails.tsx`/`MiniPlayerBar.tsx`, both `onClick={onExtract}`) had stopped working — the player just closed instead of popping out — while the `p` keyboard shortcut still worked fine. Root cause: `extractToWindow` had gone from zero-arg to `(auto = false) => …` to thread the new flag through, and React always calls an `onClick` handler with the native `MouseEvent` as its first argument regardless of the prop's declared `() => void` type (TS doesn't enforce that at the actual call site) — so clicking the button silently passed the click event itself as `auto`. That object isn't structured-cloneable, so the `extractPlayer` IPC call failed, but `setPlayerStack([])`/`setMiniplayer(false)` had already run synchronously right after it (not awaited), closing the player with no extract window ever created. The `p` path was unaffected only because `PlayerSurface.tsx`'s keydown handler calls `onExtract()` explicitly with no argument. Fixed by splitting the function in two: `extractToWindowInternal(auto: boolean)` holds the real logic, and `extractToWindow` reverts to a permanent zero-arg wrapper (`() => extractToWindowInternal(false)`) — safe to bind directly to any `onClick`/`onKeyDown` regardless of what argument the caller passes — while `handleClosedToTray` calls `extractToWindowInternal(true)` directly, never through the zero-arg wrapper. **Also added, same session (owner's own follow-up question):** the extract window loads the exact same renderer bundle/`index.html` as the main window, whose static `<title>Chronicle</title>` made both windows report the identical OS-level title — indistinguishable in a taskbar, alt-tab, or compositor window rule regardless of whether either window shows its own visible titlebar. `extractPlayer` gained a `title` parameter (threaded through `preload.ts` → the `main.ts` handler → `createExtractWindow` → the `?title=` query string → `main.tsx` → `ExtractedPlayerWindow`), which sets `document.title` to `` `${title} — Chronicle` `` on mount — Electron mirrors a page's `document.title` into the real window title by default, so no `BrowserWindow.setTitle()` call was needed on the main-process side.
