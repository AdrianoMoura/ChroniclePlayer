# D-074

**Spec:** `feed.md`, `local-data.md`

**A currently-airing live or Premiere outranks every other video regardless of date, at the actual feed-fetch/pagination level, not just on display — and a Premiere now follows the exact same upcoming/airing/ended treatment as a genuine broadcast, reversing B-119's exclusion.** Started from the product owner reporting a concrete symptom: a subscribed channel's live stream from the day before never appeared on the main feed, though it showed correctly on that channel's own screen.

**Root cause, found by investigating the owner's own `chronicle.db` directly (B-135):** the reported video's `published_at` was three days before its actual `live_started_at`/`live_ended_at` — the broadcast had been scheduled on YouTube days ahead of when it actually aired. D-053's `effectiveDate()` (`core/feed.ts`) already computes the right display position for this case, but only re-sorts an *already-fetched* page (`FeedService.getSlice`) — the underlying keyset-paginated fetch (`repositories.ts`'s `FEED_ORDER`) still ordered strictly by raw `published_at`, which D-053 deliberately never touched ("a keyset cursor can't be built on a value like `now`"). A scan of the owner's real data found this wasn't a one-off: at least 8 subscribed channels had livestreams with a multi-day scheduling gap, some buried 500–1900 videos deep in raw fetch order — past any realistic amount of scrolling, regardless of what the display-sort would have done with them if ever reached.

**Design discussion, live with the owner, revised twice:**
1. First proposal: correct the *stored* `published_at`/add a persisted sort column, keyed by `live_started_at`/`live_ended_at` once known. The owner's pushback: a stream that's *currently airing* needs to outrank everything, not just sort by when it started — a live that started an hour ago must still beat a video published 5 minutes ago, which a plain "sort by `live_started_at`" key wouldn't guarantee.
2. Final shape: a **two-tier** sort key, mirroring `effectiveDate()`'s own live-video special case but made stable enough for a keyset cursor: tier 1 is a boolean — `live_content = 'live'` outranks everything, full stop, regardless of any date comparison; tier 2 (the tiebreaker, used whenever tier 1 is equal) is the existing effective-date logic (`liveEndedAt`, clamped to never precede `publishedAt` per B-120, else `publishedAt`). Tier 1 doesn't depend on "now" changing between calls — it only flips when a broadcast's own `liveContent` actually transitions (an infrequent, real event, already relied on elsewhere, e.g. B-114's live-status re-hydration), so it's safe to bake into both `ORDER BY` and the keyset cursor's `WHERE` comparison, unlike `effectiveDate()`'s literal `now` pin.
3. **Premiere, raised directly by the owner mid-conversation ("não esqueça premieres seguem o mesmo sistema"):** B-119 (2026-07-19) had deliberately excluded Premiere from all of this — never pinned to the top while airing, `live_ended_at` never even persisted for one — reasoning a Premiere is "just a watch-along," not an open broadcast. The owner explicitly reversed that: a Premiere should be treated identically to a genuine live broadcast for ordering purposes in every stage (upcoming → `publishedAt`, airing → outranks everything, ended → `liveEndedAt`). The `is_premiere` column still exists and still gates which *badge* shows while airing ("Live" vs. "Premiere," `FeedList.tsx`'s `liveBadgeState`) — that visual distinction was untouched — but no longer gates sort/bucket order or whether `live_ended_at` gets captured.

**What changed:**
- `core/feed.ts`'s `effectiveDate()`: dropped the `&& !video.isPremiere` guard — a Premiere now pins to `now` while `liveContent === 'live'`, identically to a real broadcast.
- `adapters/storage/sync-repository.ts`'s `applyHydration`: removed the `is_premiere`-gated `CASE` that permanently blocked `live_ended_at` from ever being set for a Premiere (both the insert and update branches) — it's now `COALESCE(:liveEndedAt, live_ended_at)` unconditionally, same sticky rule a genuine broadcast already had.
- `core/ports.ts`'s `FeedCursor` (and the identically-shaped `FeedCursorDto` in `ipc/contract.ts`): grew from `{ publishedAt, channelTitle, videoId }` to `{ liveNow: boolean, effectiveDate: string, channelTitle, videoId }`.
- `adapters/storage/repositories.ts`: new `LIVE_NOW_EXPR`/`EFFECTIVE_DATE_EXPR` SQL fragments; `FEED_ORDER` is now `ORDER BY <liveNow> DESC, <effectiveDate> DESC, c.title ASC, v.video_id ASC`; `listPage`'s keyset `WHERE` clause extended to a 4-key tuple comparison; a new `cursorSortKey()` helper mirrors the SQL expressions in JS to build the next page's cursor from the last fetched row. `FeedService.getSlice()`'s own page-local re-sort by `effectiveDate()` is untouched — it still pins a live video to the literal current instant for display, which the stable `live_content = 'live'` fetch-level tier doesn't need to match exactly, only to get the row into the right neighborhood.
- `platform/ipc/validators.ts`'s `parseCursor`: validates the new shape.
- `ui/App.tsx`'s archive-backfill resume path (the one place the UI hand-builds a `FeedCursorDto` from a `FeedVideoDto`, rather than just passing one through): now computes `liveNow`/`effectiveDate` via a new shared helper.
- `ui/format.ts`: extracted `effectiveDateIso()` (previously inlined in `feedItemLabel`) so the same non-"now" effective-date computation isn't written a third time in the UI layer (which can't import `core/` directly, per `architecture.md`).

**Three existing tests codified the old, now-reversed B-119 behavior** (a Premiere excluded from the live-pin, and asserting it never gets `liveEndedAt`) — updated in place rather than left failing: `core/feed.test.ts`'s bucket/effectiveDate cases for an airing/ended Premiere now assert the same outcome a genuine broadcast gets; `sync-repository.test.ts`'s "a finished Premiere never gets liveEndedAt set" became "...gets liveEndedAt set, exactly like a genuine broadcast." Five new tests added to `repositories.test.ts` directly exercise the B-135 regression: a stale-`publishedAt` live video outranking a just-published one, reaching page 1 even when buried deep enough to have failed before this fix, the same for a Premiere specifically, an ended broadcast sorting/paginating by `liveEndedAt` rather than its stale `publishedAt`, and keyset pagination not skipping/duplicating rows when the live/ended tier and the plain-date tier are mixed across a page boundary. One fixture gap found along the way: `repositories.test.ts`'s existing `addVideo()` helper called `SqliteCatalogRepository.upsertVideo`, which (correctly, for its real production use) never writes the live-broadcast columns at all — the new tests first failed for that reason alone, not the production code; fixed by having the test helper also set `live_content`/`live_started_at`/`live_ended_at`/`is_premiere` via a direct `UPDATE`, the same fields `sync-repository.ts`'s `applyHydration` would set in production.

Checked via `npm run typecheck && npm run lint && npm test` (305/305, including the 5 new B-135 regression tests and the 3 updated B-119 ones). Not yet live-verified by the product owner — per [[no-live-app-verification]], the owner tests against a real build themselves.
