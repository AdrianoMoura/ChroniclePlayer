# D-056

**Spec:** `playback.md`, `youtube-api.md`

**Live chat panel on the player screen, via YouTube's own `live_chat` embed iframe — design agreed in conversation, not yet implemented.** A direct product-owner request, not sourced from `tracker-current.md`, same pattern as D-050–D-055. Prompted by the owner noticing other channels show chat alongside the video and wondering how it's done — confirmed it's the same mechanism YouTube's own site uses to embed chat elsewhere: `https://www.youtube.com/live_chat?v=VIDEO_ID&embed_domain=...`, a separate public embed from the Data API entirely (**zero quota cost**, no new scope). **Applies to Premieres too, not just ordinary live broadcasts** — YouTube's live chat exists for both, and Chronicle already can't tell them apart at the field level: `liveContent === 'live'` is true for a Premiere while it's airing exactly the same as for a live stream (`isPremiere` only distinguishes which red badge to show, per D-053/B-119), so gating the chat button on `liveContent === 'live'` alone already covers both with no extra condition needed. **Agreed design:** a toggle button next to the title (full player view only, shown only while `liveContent === 'live'`) opens a 500px docked column beside the video — the video shrinks for free via the existing `player-stage-slot` measurement mechanism (`PlayerSurface.tsx`/`PlayerDetails.tsx`), no new sizing logic needed. Chat always starts closed; no persisted preference — user opens it fresh each time (matches the project's general "no state the user didn't just create" bias). The column closes automatically only when the video docks to the miniplayer (the one deliberate auto-close in this design — chat has no place in the compact miniplayer bar); it also disappears for free whenever the full-view screen itself unmounts (closing the player, extracting the video to its own window), since the column is just JSX inside that screen. **Extract to an independent popup:** a second, manual "extract chat" action, separate from the video's own `p`/extract (D-051) — the two are fully decoupled, either or both can be popped out independently. Simpler than the video's own extract: no postMessage widget-protocol bridge needed (the chat iframe is passive, nothing to keep in sync), so the popup window can just `loadURL()` the `live_chat` URL directly, the same bare-window pattern the existing Sign In window already uses (`main.ts`'s `openYouTubeSignIn` handler). Needs its own distinct OS-level window title, same reason D-051 added one (the owner's niri/Wayland compositor tracks per-window title separately from the shared `app_id`). **Sign-in:** typing in the embedded chat requires the same signed-in session the video embed itself uses (`authentication.md`'s "embedded player's browser session" / B-093) — a small hint near the panel links straight to the existing `window.chronicle.openYouTubeSignIn()` IPC (same one Settings' "Sign in to YouTube" button already calls), rather than round-tripping through Settings. **Ended broadcast:** no special handling — the button simply stops rendering once `liveContent` reverts to `'none'` (same field already driving the Live/ended badge), and the embed itself natively shows chat replay or an ended notice if the user was already viewing it when it wrapped. **Explicitly still open, flagged for revisit after the owner tries it hands-on:** the popup's close/reopen behavior. Current agreed rule is the simplest one considered — once extracted, the popup stays open regardless of anything else happening in the app (miniplayer, extracting the video too, closing the player) and only closes on the user's own action on that window; closing it restores the docked column if the full-view screen is still open at that moment, otherwise it just closes with nothing to return to. A more elaborate alternative was discussed and set aside in the same conversation — auto-closing the chat popup specifically when the video docks to the miniplayer (mirroring the column's own miniplayer auto-close), while still leaving it independent of extracting the video — the owner wants to live with the simpler rule first and may revert to that alternative once they've actually used it. **Status: Final — merged to main 2026-07-23, live-tested and confirmed working by the product owner.** New `PlayerVideoDto`-driven UI (`PlayerDetails.tsx`'s title-row toggle and `.player-stage-row`/`.player-chat-column`), a new IPC round trip (`extractChat`/`chat:extractWindowClosed`, `main.ts`'s `createChatWindow` — a bare `loadURL()`, no preload/postMessage bridge), and the App.tsx-level `chatSurface` state machine (`'closed' | 'column' | 'extracted'`, with `miniplayerRef`/`currentPlayerVideoIdRef` mirrors so the popup-close event handler can read live state without resubscribing) implement the design above, including the still-open popup-behavior caveat. **Fixed during the owner's own live test, same session:** the docked column rendered as a blank white box — the embedded `live_chat` iframe was missing `embed_domain`, which YouTube's embed requires when framed (the pop-out window worked fine regardless, since it's a top-level navigation rather than an iframe); Chronicle's renderer always runs on `localhost` (dev server or the packaged app's own local static server, never `file://`), so `embed_domain=localhost` fixed it. **Also adjusted per the owner's same-session feedback:** the toggle button relabeled to "View live chat" / "Ver chat ao vivo" with a smaller font; the column's own extract button moved from sitting right under the video's own extract button (confusingly close together) down to share a row with the sign-in hint, aligned right; an (i) tooltip icon added next to the sign-in hint (same native-`title` pattern as the sync status icon, B-105, `cursor: pointer` added to both) explaining that live chat is a YouTube embed, so Chronicle's own session doesn't carry over and a separate one-time sign-in is needed; `openYouTubeSignIn()` gained an optional `title` param (same mechanism `extractPlayer` already had, for the same niri/Wayland per-window-title reason) so the popup opened from the chat's own sign-in link is titled "Sign in for Live Chat" instead of inheriting the generic "YouTube" page title; and Settings' existing `playerSessionNote` (which already described the embedded player's separate browser session) was extended to mention that the same session covers live chat too, since Settings' own "Sign in to YouTube" button is the same one-time sign-in.
