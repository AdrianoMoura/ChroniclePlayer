# D-053

**Spec:** `feed.md`, `local-data.md`

**A currently-live video sorts to the top of its date bucket; an ended broadcast sorts — and buckets — by when it actually ended, not its original (older) `publishedAt`.** Supersedes the plain "publishedAt descending, nothing else influences order" reading of `feed.md`'s original Ordering rule for this one case. A direct product-owner request, raised in conversation rather than through `tracker-current.md`: a livestream that's been running for hours keeps the `publishedAt` of when it started, so it sinks below every video published since — exactly backwards for content that's still actionable *right now*. **First design floated and rejected in the same conversation:** a separate bucket-less "Live now" priority section above the chronological groups, mirroring B-042/D-039's favorited-channels section — the owner explicitly said no, they wanted this to stay "just a matter of ordering" within the existing listing, not a new section. **Second design, also revised the same conversation:** an initial pass reordered entries *within* each contiguous same-bucket run only, deliberately never crossing a bucket boundary, using a sort key (`effectiveLiveTime`: `Infinity` while live, else `liveEndedAt`, else `publishedAt`) that was separate from the plain-`publishedAt` value still driving bucket assignment. The owner's own follow-up question caught the gap this left: a broadcast that starts at 20:00 and ends at 02:00 the next day would sort correctly within its bucket but still display under **Yesterday** (its start date), not **Today** (when it actually wrapped) — sorted right, grouped wrong. **Design actually shipped:** `core/feed.ts`'s `effectiveDate(video, now)` is now the **one** value driving both bucket assignment (`bucketOf`) and sort order (`compareFeedOrder`/`FeedService.getSlice`'s page sort) — never two different timestamps for the two decisions, precisely because that mismatch is what caused the midnight-crossing gap. `effectiveDate` is `now` while `liveContent === 'live'` (so a live video always sorts to the top of *Today*, however long ago it actually started, since it's still happening); `liveEndedAt` once a real end time is known (checked directly, not gated on the sticky `wasLive` flag — a video whose first-ever hydration lands after its broadcast already ended, e.g. late gap-backfill, would have `liveEndedAt` set but `wasLive` still false, since `wasLive` only flips on an observation while genuinely live); otherwise the video's own `publishedAt`, unchanged — so ordinary uploads and every video that was never live are entirely unaffected, both in sort position and bucket. Applied in `FeedService.getSlice()`: the already-fetched page is sorted by `effectiveDate` before each entry's bucket is (also) computed from it — display-only, never touches keyset pagination (D-027), since a keyset cursor can't be built on a value like `now` that changes between calls; the cursor for the *next* page is still derived from the raw, un-reordered, plain-`publishedAt`-ordered SQL rows (`repositories.ts`'s `FEED_ORDER`, deliberately left as `publishedAt DESC` and documented as intentionally divergent from `compareFeedOrder` now). **The owner's own separate follow-up, same conversation:** noticing Chronicle already tracks whether a broadcast has ended (B-114's sticky `wasLive`), they asked whether the *actual end time* could drive ordering, once a stream wraps — it wasn't captured at all before this decision. `liveStreamingDetails.actualEndTime` was already riding along on the existing `videos.list` hydration call (`part=liveStreamingDetails`, no extra quota, same as B-115's `concurrentViewers` check) but was never read. New `videos.live_ended_at` column (schema v12, nullable `TEXT`), threaded through `HydratedVideo.liveEndedAt` / `Video.liveEndedAt`; `sync-repository.ts`'s `applyHydration` persists it sticky via `COALESCE(:liveEndedAt, live_ended_at)`, the same pattern `was_live` (v10) already established — once a real end time is captured, a later cycle that (for any reason) doesn't report one again can never clear it. **Also extended, same conversation, the owner's own follow-up:** noticing `liveEndedAt` can be known without `wasLive` ever having been true, the owner asked whether the feed's existing gray "ended" badge (B-114) could benefit the same way — it couldn't before this, since `liveBadgeState` (`FeedList.tsx`) only checked `wasLive`. `FeedVideoDto` gained a `liveEndedAt` field (threaded through `toVideoDto`, `main.ts`) and `liveBadgeState` now shows 'ended' on `video.wasLive || video.liveEndedAt` — so a video whose broadcast-ended status is only known via `liveEndedAt` (never observed live, e.g. late gap-backfill) now gets the same visual badge as one caught live and later re-hydrated post-broadcast, not just the correct ordering. Checked via `npm run typecheck && npm run lint && npm test` (`core/feed.test.ts` covers `effectiveDate` in isolation plus `groupFeed` integration cases including the midnight-crossing scenario; `adapters/youtube/api-client.test.ts` covers `actualEndTime` parsing; `adapters/storage/sync-repository.test.ts` covers the sticky persistence); not run live — needs the owner's own hands-on check against a real live/just-ended broadcast.
