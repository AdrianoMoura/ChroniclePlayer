# D-046

**Spec:** `playback.md`

**Miniplayer continuity (`bugs.md` [[B-045]]): docking to the corner keeps the exact same live `<iframe>` instance mounted (no restart); extracting to an always-on-top window cannot, and hands off a playback snapshot to a fresh instance there instead.** Two different answers for what looked like one question, because they're not the same technical problem. Extracting opens a second `BrowserWindow` (`alwaysOnTop: true`) — a genuinely different renderer process, so the DOM node itself cannot move there — loading the exact same renderer bundle with an `?extract=<videoId>&t=<seconds>&autoplay=<0|1>` query string that `main.tsx` checks to render a bare, chrome-less `ExtractedPlayerWindow` instead of the full app; the main window's player then closes outright, since playback now lives in that window. Docking stays within the same renderer process, so the same live iframe *should* be able to keep running — **first attempt got this wrong**: it used a React portal to move the iframe between a full-view slot and a corner-box slot, which shipped and immediately restarted the video on every dock in the owner's live test, because moving an `<iframe>` to a different DOM parent (exactly what a portal does, even without detaching it from the document) makes Chromium reload it — a browser behavior, not a React bug, not fixable by portaling "more carefully." **Revised same day**: dropped the portal; `PlayerSurface` now renders at one permanently stable tree position and never moves in the DOM at all, instead measuring whichever slot placeholder (`ResizeObserver`-watched, in a non-scrolling region so scroll ticks don't need tracking) the active layout (`PlayerDetails` or `MiniPlayerBar`, both still always-mounted, CSS-hidden when inactive) provides, and mirroring that rect via `position: fixed` inline styles. Also added, per the owner's same live-test feedback: the corner box is resizable (native `resize: horizontal`, default width raised from 260px to 360px) and the explicit "Miniplayer" button was removed — the owner's actual ask was automatic-only docking on leaving a playing video, and the manual button read as redundant clutter once that automatic path worked. Per the product owner: both docking and extraction legs landed in the same pass, accepting the reload for the extract leg as an inherent limitation of crossing a process boundary, not something to keep chasing a workaround for. **Revised again same day, third round**: the next live test found docking didn't fire via *any* path — root causes were (a) every "hard" navigation-away action (sidebar clicks, search submit, account switch) called `setPlayerStack([])` directly, never consulting the dock decision at all, fixed with a shared `leavePlayerForNavigation()` that collapses the stack to the current video and docks it if still going; and (b) the dock decision itself was gated on the IFrame API's literal `PLAYING` state, which depends on an `onStateChange` round trip not reliable enough to gate a core feature on — loosened to "still going" (true unless explicitly paused or ended), exposed as `PlayerSurfaceHandle.isStillGoing()`. **Revised again same day, fourth round**: the next live test surfaced six more gaps, all fixed in this pass. Extraction gained a return path — closing the always-on-top window now broadcasts `player:restoreFromExtract`, which re-opens that video docked in the main window — and reliable autoplay, by having `ExtractedPlayerWindow` speak the same postMessage widget protocol as the main player (`enablejsapi=1`, explicit `command('playVideo')` after handshake, `autoplayPolicy: 'no-user-gesture-required'`) instead of trusting the embed's own `autoplay=1` alone under Electron's stricter top-level-navigation policy; the same protocol's `infoDelivery` messages are what let the restore resume close to the actual playback position (persisted via `beforeunload` → `setResumePosition`). The extract window (and, once noticed, the B-093 sign-in window) now also calls `removeMenu()` — neither should show Electron's native menu bar. The resize handle moved from native CSS `resize: horizontal` (which anchors its own grab handle to the box's bottom-right corner — exactly where the whole box already sits against the screen's corner, making it awkward to grab) to a custom top-left drag handle, with the resulting width persisted as `miniplayerWidth` in settings rather than resetting every launch. And a real navigation-stack bug was fixed: opening a video from any *fresh browsing* action (feed, search, priority/channel-preview sections, URL prompt) now explicitly replaces the stack instead of defaulting to push mode, so docking one video and then opening an unrelated one no longer buries the first one for Back to surface later — push mode is now reserved for the one case it's actually meant for, opening a video via an in-description link while watching another. **Revised again same day, fifth round**: the fourth round's own resize-handle and extract-autoplay fixes turned out not to work either, both for reasons specific to how those fixes were built rather than the underlying ideas being wrong. The resize handle was positioned `absolute; top: 0; left: 0` *inside* `.miniplayer` (z-index 20) — but the video itself is a separate always-mounted element (`.player-stage`) mirroring the stage slot's rect at z-index 21, one layer above, painted directly over that same corner: no z-index tweak on the handle could win, since a child can never paint above a sibling stacking context with a higher z-index than its own parent's. Fixed by giving the handle real layout instead — `.miniplayer` is now a flex row of a fixed-width left-edge strip plus a `.miniplayer-content` column holding the video slot and title bar, so the mirrored iframe (which only ever covers the stage slot's own rect, now inset by the strip) structurally cannot overlap the handle. Separately, the extract window's autoplay fix from last round was correct but never actually exercised: `extractToWindow` hands the extract window a `playing` flag read from `PlayerSurface`'s `getPlaybackSnapshot()`, which used the exact same overly strict `playerStateRef.current === 1` check that round three of this same decision already found and loosened for the *docking* decision (`isStillGoing()`) — `getPlaybackSnapshot` had simply never been updated to match, so it kept handing off `playing: false` whenever the autoplay-initiated `onStateChange` round trip hadn't landed yet, and the extract window's autoplay logic was faithfully honoring that (correct) instruction. Fixed by having `getPlaybackSnapshot().playing` reuse `isStillGoing()` too. **Revised again same day, sixth round**: the owner found D-038's default playback speed wasn't reaching the extracted window at all — it always opened at 1x. Root cause: `extractPlayer` never had a `defaultPlaybackRate` parameter in its IPC signature, so there was no path for the setting to travel through at all (unlike the main player, which gets it as a normal prop from `App.tsx`'s `settings` state) — not a bug in the widget-protocol plumbing itself, just a parameter that was never added when `extractPlayer` was first written. Fixed by threading it through every layer (`ChronicleApi.extractPlayer` → `preload.ts` → the `main.ts` IPC handler, validated against `PLAYBACK_RATES` server-side → `createExtractWindow` → the `?extract=` query string's new `rate=` param → `ExtractedPlayerWindow`), which applies it exactly the way `PlayerSurface` applies D-038: `setPlaybackRate` on the widget-protocol handshake, reissued on the `onStateChange` transition to playing, since YouTube can reset it back to 1x once the stream actually starts. **Revised again same day, seventh round**: the owner found the full-view player screen no longer scrolled as one page — a deliberate trade-off from the first round (a non-scrolling topbar+stage flex row so the stage slot's rect never moved, meaning `PlayerSurface`'s `position: fixed` mirroring never had to re-measure on scroll) that, once actually lived with, wasn't wanted: the video should scroll away with the rest of the page like a normal page, not stay pinned above a separately-scrolling info panel. Fixed by reverting `.player-view` to one normally-flowing scrolling block and teaching `PlayerSurface`'s measurement effect to also re-measure on scroll (not just resize), throttled to one `requestAnimationFrame` per tick — using a `window`-level `scroll` listener with `capture: true`, since scroll events don't bubble but do fire during the capture phase on ancestors, letting one listener there catch `.player-view` scrolling without a direct reference to it. **Revised again same day, eighth round** (plus the product owner's own request to raise the miniplayer's max resizable width from 640px to 1024px, `MINIPLAYER_MAX_WIDTH`): the sixth round's extract-window default-speed fix still didn't work live. The wiring itself (Settings → IPC → query string → `ExtractedPlayerWindow`) was correct; the bug was in the reissue mechanism, which reused D-038's normal pattern of reissuing `setPlaybackRate` on the iframe's `onStateChange(playing)` message — but the third round of this same decision already established that the *autoplay-initiated* `onStateChange` isn't reliably observed at all, the exact same reason `isStillGoing()` and the fifth round's extract-autoplay fix both had to stop trusting a strict state check. The rate reissue had simply never been given the same treatment. Fixed by reissuing on every `infoDelivery` message instead — a steady heartbeat once the widget is genuinely up, independent of which `onStateChange` events happened to land — for the first 3 seconds after load (wall-clock time, not video position, since most extractions hand off mid-video). **Exercised 2026-07-15**; needs the owner's own live validation (dock via Back/Esc, dock via sidebar navigation, maximize, resize + persistence, extract, extract autoplay, extract at the configured default speed, close-extract-to-restore, no menu bar on the extract window, replace-vs-push across all open paths, full-view page scroll with the video scrolling smoothly, and the modal-vs-miniplayer stacking order — `.overlay-backdrop` was given `z-index: 30` specifically so help/consent dialogs stay on top of a docked miniplayer) before considering this closed.
