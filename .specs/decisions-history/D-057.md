# D-057

**Spec:** `feed.md`, `playback.md`

Three Watch Later refinements, all direct product-owner requests, same session, same pattern as D-050–D-056.

**(1) Auto-remove from Watch Later on open.** New `SettingsDto.watchLaterAutoRemove`, default **off**. While on, opening a video that's currently queued removes it from Watch Later immediately — the same effect as a manual untoggle, just triggered by opening rather than a click. No undo strip, per the owner's own call: a queued video already stays visible in the current in-memory list until the view is left and reopened, the same grace a manual untoggle already has, so a second undo mechanism would be redundant.

**(2) Up-next card wraps around.** The player's "up next" card (D-055) now wraps: reaching the last queued video suggests the oldest one again instead of going silent, since the user can start watching from anywhere in the queue, not just the front — combined with (1), this lets a user work through their whole queue by just opening videos. Guarded against suggesting the video that just ended (a one-item queue no longer loops onto itself). `core/feed.ts`'s `nextWatchLaterAfter` now uses modulo wraparound instead of returning `null` past the last index.

**(3) Drag-and-drop reorder in the Watch Later view — a long, mostly-wrong iteration.**

Native HTML5 drag-and-drop, no new dependency (the owner's own call, given the project carries no DnD library). This part went through several rounds live-tested by the owner, most of which were wrong guesses on my part rather than confirmed fixes — recorded here in full because the failure pattern itself is the useful part for next time.

- **Round 1.** Whole row/card draggable, drop computed from which half (top/bottom for a list row, left/right for a grid card) the pointer was over within the *whole item*, via `event.currentTarget.getBoundingClientRect()`. List-layout only at first; grid support and the "no separate grab handle, whole item is the drag source" call came the same session, still round 1.
- **Round 2 (owner's live catch): the border-on-the-hovered-item feedback didn't read as "insert here", and dropping past the last item didn't work at all.** Guessed the fix was the *visual* (border → a `.drop-gap` element) plus a same-item-gets-two-positions ambiguity, and added a dedicated leading/trailing gap **child of each row/card**, positioned via a hand-picked negative CSS offset (`top:/left:/right:/bottom: -Npx`) guessed to center it in the gap between items.
- **Round 3 (owner's live catch): still broken — grid never showed a highlight or reordered at all; list showed the highlight but the drop silently no-opped; the indicator sat flush against one neighbor, not centered.** This time actually derived the pixel geometry instead of guessing: the offset in round 2 assumed a fixed margin/slack between items, but that slack varies by item size for list rows and isn't fixed at all for a dynamically-columned grid — so the indicator was genuinely mispositioned, not just cosmetically off. Rebuilt on exact geometry: list drop targets became real virtualized rows of their own (`DisplayRow`'s `'gap'` kind, `GAP_ROW_HEIGHT` reserved in the virtualizer, automatically equidistant since position comes from the same layout math as every other row); grid drop targets became bars positioned by the *same pixel formula* driving the grid's own `1fr` columns (`cardWidth` promoted from a local variable to state so both read the same number). Also dropped the "faint ambient strip for the whole drag" state per the owner's preference — gaps now stay fully invisible until hovered.
- **Round 4 (owner's live catch): still broken in the exact same way — list intermittent, grid never, drop always a no-op.** Since the geometry fix in round 3 didn't change the actual symptom at all, the geometry was never the real bug — a case of finding a plausible-sounding explanation and committing to it without verifying, twice. Re-examined from the actual HTML5 drag-and-drop event lifecycle instead of CSS layout: `.row`/`.card` never had `user-select: none`, and most of a row/card's clickable surface is text (title, channel name, meta line). Starting the drag gesture on top of that text makes Chromium begin a native **text-selection drag** instead of respecting the ancestor's `draggable=true` — this component's own `dragstart` never fires, `dragIndex` stays `null`, yet a real (text) HTML5 drag session is still in progress and can still fire `dragover` on the invisible-until-hovered gap elements below it. That produces exactly the reported symptoms: a highlight that looks intermittent (it only shows when the gesture happens to start on non-text — thumbnail, padding, badges), and a drop that always silently no-ops (`commitReorder` correctly refuses to act with `dragIndex === null`). Fixed by adding `user-select: none` (plus `-webkit-user-drag: element`) to `.row.reorderable`/`.card.reorderable`.

`onReorder(fromIndex, insertAt)` — the gap/drop-target itself already carries the exact insertion index, no before/after side to disambiguate. Persists through a new `reorderWatchLater(videoIds)` IPC call (`StateRepository`) that reassigns `watch_later_pos` from the dropped order in one transaction, ignoring any id no longer in the queue.

**Not yet confirmed by the owner's own live test past round 4.** Given three consecutive wrong "fixes" that each passed `npm run typecheck && npm run lint && npm test` while the actual interaction stayed broken, that test suite covers none of the DOM/CSS/native-drag-event behavior this feature depends on — it can only catch logic bugs in the reorder math, not whether a drag actually starts, is tracked, or lands.
