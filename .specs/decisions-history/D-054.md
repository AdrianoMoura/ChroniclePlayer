# D-054

**Spec:** `ui.md`, `architecture.md`

**Localization: a Settings language dropdown (first section on the screen), defaulting to "Follow system," backed by a locale registry discovered at build time — not a hand-maintained list.** A direct product-owner request, not sourced from `tracker-current.md`, same pattern as D-050/051/052/053. Every UI string already lived in one place (`ui/i18n`, B-017's `t(key, vars)` lookup) with only an English dict; this decision turns that into a real multi-locale system. **Registry mechanism, the actual point of the design:** `src/ui/i18n/locales/*.ts`, one file per locale, each exporting `meta: { code, nativeName }` plus `dict: Partial<Dict>` (English's `locales/en.ts` is the only full, non-partial one — the source of truth for the key set). `src/ui/i18n/index.ts` discovers all of them via Vite's `import.meta.glob('./locales/*.ts', { eager: true })`, so **contributing a translation is only a PR adding one new file** — no registry to edit, no other code to touch, matching the product owner's explicit ask. A translation is deliberately allowed to be partial (`Partial<Dict>`, not `Dict`): `t()` falls back to English per missing key, so a contributed locale can lag behind new strings added after it shipped without ever breaking the build or showing a blank string. **Default = "Follow system":** `SettingsDto.language`/`AppSettings.language` is a plain `string` (not a union of shipped codes) — `'system'` is the persisted sentinel; any other value is a locale code. Resolution happens entirely in `ui/i18n` (`detectSystemLocale()`, reading `navigator.languages`/`navigator.language`, exact-code match first then base-subtag match, e.g. a `pt-PT` system falls back to the shipped `pt-BR`), never in `platform/` — `settings-store.ts`'s `normalizeSettings` only checks "is this a non-empty string," deliberately decoupled from which locales happen to exist, so the settings layer never needs updating when a locale is added or removed. **Applying a change without a restart:** `t()` reads a module-level `activeCode` that `setLocale(language)` reassigns; since nothing here is React state, the switch only takes visible effect on components that re-render afterward — so `App.tsx` calls `setLocale()` synchronously at both points that ever change `settings.language` (initial `getSettings()` load, and `changeSettings()`), strictly *before* the `setSettings()` call that (already, for unrelated reasons) re-renders the whole tree — no extra state, no flash of the old language, no memoized component in the tree to fight (verified none exists). **Ships with English (complete) + Portuguese/Brazil (complete) at launch.** **Revised same day, the owner's own live catch:** switching languages left the sidebar's view labels (All/Unread/Watch Later/Favorites/Ignored) stuck in whatever language was active first. Root cause: three call sites baked `t()` into a module-level constant evaluated once at import time — `Sidebar.tsx`'s `VIEW_LABELS`, `App.tsx`'s `BUCKET_LABELS` (feed date-bucket headers), and `onboarding/Wizard.tsx`'s `CONSOLE_STEPS` (the Google-console step text) — none of which ever re-ran on a later `setLocale()` call, unlike every other `t()` call in the app, which sits directly in a component's JSX and therefore re-evaluates on every render. Fixed by converting all three into plain functions (`viewLabel()`, `bucketLabel()`, `getConsoleSteps()`) that call `t()` only when invoked, called fresh at render time instead of once at module load. One of the three needed a second fix beyond that: `App.tsx`'s feed `rows` were built inside a `useMemo` keyed only on `[filtered]`, so even after `bucketLabel()` stopped being frozen, the *memoized result* embedding its output still wouldn't recompute on a pure language switch (no video-list change) — added `settings.language` to that memo's dependency array (with an `eslint-disable-next-line react-hooks/exhaustive-deps`, since the rule can't see that `bucketLabel()` reads module-level i18n state through `t()`). **Also added, prompted by the owner noticing they had no way to change the language before ever reaching Settings:** a language dropdown on the wizard's Welcome screen (`WelcomeStep`, reusing the same `settings.language.*` strings and `AVAILABLE_LOCALES` list as the Settings dropdown) — the wizard runs before Settings is reachable at all, so "Follow system" was previously the only option available during onboarding. `WizardProps` gained `language`/`onLanguageChange`, threaded from `App.tsx`'s existing `settings`/`changeSettings` at both `<Wizard>` render sites (first-run and Settings re-entry). Checked via `npm run typecheck && npm run lint && npm test` plus a production build; the module-level-staleness class of bug is now something to watch for in any *future* `t()` usage outside a component's render body.
