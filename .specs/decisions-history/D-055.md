# D-055

**Spec:** `playback.md`, `non-goals.md`

**Player "up next" card: on video end, a floating bottom-right card suggests the next video from the user's own Watch Later queue — thumbnail + title + an explicit Open button, no autoplay, dismissible.** A direct product-owner request, not sourced from `tracker-current.md`, same pattern as D-050–D-054. Distinct from D-021's existing `n` keyboard shortcut (only active when the playing video was itself opened *from* the Watch Later feed view, via `App.tsx`'s `queueRef` navigation-context tracking): this suggestion is derived purely from data, not navigation history, so it also fires for a video that was never queued at all, or reached by any other path (search, external link, another queued video's own description link). **FIFO rule, confirmed by the owner in the same conversation:** the video that just ended isn't in the queue → suggest the oldest-queued item (`listWatchLaterQueue`'s own `watch_later_pos ASC` order); it is in the queue → suggest whichever entry follows it. No suggestion once the queued video that ended was the last one, or the queue is empty. New pure function `nextWatchLaterAfter(queue, currentVideoId)` in `core/feed.ts` (unit tested offline, `feed.test.ts`), wired through `FeedService.getNextWatchLater()` → new IPC `feed:nextWatchLater` → `ChronicleApi.getNextWatchLater(videoId): Promise<FeedVideoDto | null>`. `PlayerSurface` gained an `onEnded` callback firing once per real ended transition (the same `onStateChange` `info === 0` branch that already clears the resume checkpoint); `App.tsx` looks up the suggestion and renders `UpNextCard` — a static, non-modal, bottom-right floating card (same corner as the miniplayer, but the two never coexist: shown full-view only, `!miniplayer`), with its own dismiss (×) and an Open button that opens the suggested video via the existing `openVideo(id, 'replace')` path, exactly like any other manual navigation. No timer, no countdown, no auto-advance — a click is the only way anything plays, keeping this inside `non-goals.md`'s "no autoplay into other videos" carve-out for an explicit, user-built queue. Cleared whenever the video changes (any `openVideo` call) or the player closes, so a stale suggestion never lingers onto an unrelated video. **Scope note (an assumption, not yet confirmed live):** the card only renders in the full player view, not the miniplayer or the extract window — the miniplayer already occupies the same corner, and the extract window is a separate, chrome-less renderer with nowhere to put it; worth revisiting if the owner wants it to also surface while docked. **Fixed the same day, the owner's own live catch — the card never appeared at all:** the initial `onEnded` hookup only fired from the `onStateChange` postMessage event's `info === 0` branch, but reaching "ended" is *always* embed-initiated (Chronicle never issues a command to stop a video; YouTube's own player just decides it's done) — exactly the class of transition B-111 already found the one-shot `onStateChange` round trip unreliable for. Fixed the same way B-111 fixed `isStillGoing()`: the `infoDelivery` heartbeat (`PlayerSurface.tsx`) is now also a detection path for `playerState === 0`, with a `handleEnded()` guard (a plain closured boolean, reset whenever state moves off 0) keeping the resume-checkpoint clear and the up-next lookup one-shot regardless of which event notices the transition first. Checked via `npm run typecheck && npm run lint && npm test`; not run live — needs the owner's own hands-on check that the card now actually appears on a real video ending.
