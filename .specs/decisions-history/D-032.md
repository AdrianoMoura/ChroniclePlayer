# D-032

**Spec:** `authentication.md`, `non-goals.md`, `features.md`

**Scope policy: minimal at start, incremental by feature.** Initial auth requests `youtube.readonly` only. YouTube-side interaction features — subscribe, **like, comment** — are planned (not banned), each unlocking via incremental authorization (`youtube.force-ssl`) the first time the user invokes it. Chronicle-side local states still never sync (D-003). What remains banned is Chronicle-generated engagement *mechanics*, not the user expressing themselves on YouTube. **Implemented 2026-07-12 ([[B-006]]):** like a video (`videos.rate`/`.getRating`), read a video's comment thread (`commentThreads.list`, no write scope needed), post a top-level comment (`commentThreads.insert`) and reply to one (`comments.insert`). **API gap found while implementing, not a product choice:** the public YouTube Data API v3 has no endpoint to like a *comment* — only videos. Comment `likeCount` is shown read-only; there is no like button on a comment. **Revised 2026-07-13 (`bugs.md` B-067):** the first four incremental-consent call sites (like, subscribe, post comment, reply) originally opened the system browser for Google's consent screen the instant a write action was attempted, with no in-app warning — jarring, since the user had no reason to expect their click to pop open a browser tab. Each of those IPC handlers now returns a `write-scope-required` result instead of silently triggering the flow; the renderer shows an explanatory confirm dialog first (`useWriteScopeGate`), and only calls the new dedicated `requestWriteScope` IPC method (which does what those handlers used to do inline) once the user confirms. Unsubscribe's own incremental-consent call site (per-account, not the shared primary-account `authFlow`) was **not** converted — same gap remains there, noted as a known limitation in `bugs.md`. **Revised again 2026-07-13 (`bugs.md` [[B-081]]):** unsubscribe's gap is closed via a channel-scoped `requestWriteScopeForChannel(channelId)` IPC (resolves the owning account instead of assuming the primary one) and an optional second argument on `useWriteScopeGate.run()` for callers that need a non-default consent request. Separately: reading comments (`commentThreads.list`) turns out to also require the write scope in practice, not just readonly as this decision originally assumed — confirmed by the owner's live testing (granting the scope via Like is what makes comment-reading start working). Gated the same proactive way as every other write action rather than carved out as a special case.
