# D-050

**Spec:** `features.md`, `architecture.md`, `non-goals.md`, `local-data.md`

**Tray-resident mode, OS auto-start, and opt-in new-video notifications — three fully independent Settings toggles, all default off; none gates any other.** **(1) Auto-start** — launch Chronicle on OS login: Electron's `app.setLoginItemSettings()` (Windows Registry Run key / macOS LaunchAgent, both built-in); Electron has no Linux equivalent, so `src/platform/linux-autostart.ts` hand-writes/removes an XDG `~/.config/autostart/*.desktop` entry (plain `fs`, no native module, D-034-compliant). **(2) Run in background** — closing the window hides it to a tray icon (`src/platform/tray.ts`, Electron's cross-platform `Tray`) instead of quitting; the tray menu is Open Chronicle / Refresh now / Quit. This is what lets the existing 30-min sync timer (D-016) keep running with no window open. **(3) New-video notifications**, via Electron's cross-platform `Notification` API — **corrected during implementation (2026-07-16, the product owner's own catch):** the original spec-only pass wrongly UI-disabled this toggle unless (2) was on, reasoning that "the app isn't alive to notice anything" otherwise — false, since the app is already alive any time its window is open at all (that's the existing D-016 timer, untouched), regardless of "Run in background." (2) only extends *when* the process stays alive (surviving window-close); it was never a hard prerequisite for (3). Settings now shows an informational note near the toggle instead of disabling it. Never fires on an account's first sync (`SyncReport.firstSync`) — that's backlog, not something that happened while backgrounded (mirrors D-047's reasoning). Notification scope is one segmented choice, not three settings: **All channels** · **Favorites only** (reuses the existing favorite-channel flag, zero new schema) · **Custom** — realized as a **new per-channel `notify` flag** (`account_channels.notify`, schema v9) toggled from the sidebar channel's own "⋯" context menu exactly like Favorite/Unfavorite, per the product owner's standing preference for inline per-item controls over a Settings checklist — Settings only shows the scope picker plus a hint pointing at that menu. `SyncService.refresh()` (`src/core/sync-service.ts`) gained a free-information per-channel tally, `SyncReport.newVideosByChannel`, from the same per-channel discovery loop that already existed — core stays notification-agnostic; the scope/first-sync policy lives in `main.ts` where the feature actually is. **Rejected alternative:** an OS-level scheduled task (Task Scheduler/launchd/cron) launching Chronicle headlessly just to sync+notify, then exit — three separate per-OS scheduling implementations instead of reusing the sync machinery that already exists, for no real resource saving over just staying resident. **Verification risk (Assumption, not yet confirmed):** the product owner's hands-on verification is Linux-only (`roadmap.md`'s M0 exit criterion), so the Windows/macOS auto-start and notification paths — including whether D-043's unsigned/non-notarized macOS build degrades Notification Center registration — cannot be live-verified directly; every capability feature-detects and disables itself silently rather than throwing/crashing if unavailable on a given platform. **Revised same day, redesign round (owner's own written spec, 2026-07-16):** three bugs and one UX redesign, found the moment the owner actually tried tray-resident mode live. **Bugs:** (a) toggling "Run in background" on/off repeatedly appeared to leave multiple ghost tray icons behind, one of which never disappeared — root cause wasn't the toggle logic itself (which was already correctly gated on `tray === null`) but a missing `app.requestSingleInstanceLock()`: before this feature, closing the window always quit the process, so relaunching (e.g. restarting the dev server) never left a stale instance; now that the window can close without quitting, a second launch on top of an already-tray-resident first instance spawns a fully independent second process with its own tray icon, and toggling Settings in one instance can't touch the other's — fixed by adding the lock plus a `second-instance` handler that just re-shows the existing window. (b) A real, separate correctness bug found during the fix: `applyBackgroundMode`'s disable branch called `tray?.destroy()` then `tray = null` inside one `try` — if `destroy()` ever threw, the reset line never ran, leaving `tray` referencing a possibly-dead object and blocking any future recreation; pulled into its own `destroyTray()` helper with its own try/catch so the reference always clears. (c) Emoji removed everywhere per the owner's direction: the sidebar's old notify menu item (superseded anyway by the redesign below) and, flagged in the same pass despite predating D-050 entirely, the like button's 👍 (`player.action.like`/`liked`) — dropped to plain text, matching every sibling action label (subscribe/ignore/watch-later), which already carry no icon and rely on the existing `active`-state styling instead. **Redesign:** collapses the notification *scope* from three choices to two — **All Channels** (ignores the per-channel flag) and **Selected Channels** (respects it) — dropping "Favorites only" as a distinct scope entirely; a new global convenience toggle, **auto-enable notifications when favoriting**, syncs the per-channel `notify` flag to a channel's favorite state at the moment either is toggled (one-shot nudge, not a live binding — a later manual notify change on that channel is never re-overridden until the next favorite/unfavorite). Turning the convenience toggle *on* immediately bulk-applies notify=true to every current favorite, no confirmation needed; turning it *off* always takes effect immediately but additionally asks (a `write-scope-dialog`-styled confirm overlay, reusing `useWriteScopeGate`'s existing visual pattern) whether to also bulk-clear notify from current favorites — declining leaves every per-channel flag untouched. **Configuration preservation, explicit invariant:** neither switching `notifyScope` nor toggling `notifyNewVideos` off/on ever writes to the per-channel `notify` column — both are pure read-side filters (`main.ts`'s `maybeNotifyNewVideos`), so a "Selected Channels" configuration survives being ignored while "All Channels" or the global toggle is temporarily active, and reappears exactly as left once switched back. Per-channel control moved out of the sidebar's "⋯" overflow menu into a **directly clickable, always-visible icon** (`●` filled / `○` outline — plain glyph, no emoji, matching the existing `★`/`☆` favorite convention) placed immediately before the "⋯" button, shown only when `notifyNewVideos && notifyScope === 'selected'` (hidden the rest of the time since it would have no effect) — and the identical control was added to the channel details page next to the existing `★`/`☆` Favorite button, both driving the same `toggleChannelNotify` IPC call so either surface always reflects the other. New repository primitives backing the convenience toggle: `setChannelNotify` (direct set, not toggle) and `bulkSetNotifyForFavorites` (`UPDATE ... WHERE favorite = 1`) — no schema change, same `account_channels.notify` column from the original pass. **Revised again same day** (UI polish + a live-tested tray fix): the ●/○ dot glyphs were replaced with a small inline monochrome SVG bell (`src/ui/icons.tsx`, `currentColor`-based, filled/outline mirroring ★/☆) since Unicode has no non-emoji bell character (🔔/🔕 default to colored emoji presentation) — the owner asked for an actual bell shape once emoji were ruled out. Favorite was also moved out of the sidebar's "⋯" menu into its own always-visible ★/☆ row button (same pattern as the notify icon), leaving only Unsubscribe in the menu. **Tray duplication, root-caused via live testing, not guesswork:** the owner's live retest, after the single-instance-lock fix, still hit stuck/duplicate tray icons **within one running process** (toggling the Settings checkbox alone, no relaunch involved) — narrowing the fault to `destroy()` itself not being honored while the process stays alive. Live D-Bus introspection (`busctl --user call org.kde.StatusNotifierWatcher ... RegisteredStatusNotifierItems`) during a stuck-icon state showed **zero** live Chronicle registrations, while the ghost icons stayed visible and stopped responding to clicks/context-menu — proof they were dead delegates in the tray host's (QuickShell, `qs -p .../dms`) own rendering state, not anything Chronicle still held open. Quitting the app fully (which drops the whole D-Bus connection rather than sending an explicit unregister) reliably clears the icon, confirming the host handles connection-loss cleanup fine but not an explicit live unregister. Two speculative fixes were tried and both reverted: (i) `tray.setContextMenu(null)` before `destroy()` — unproven two-step teardown, no confirmed improvement; (ii) a fixed `guid` on `new Tray(icon, guid)` — Electron validates this against a strict format and threw `Invalid GUID format` live on this exact setup (caught by the existing try/catch, so no crash, but no tray got created either) — reverted outright once confirmed **not** the free/harmless addition it looked like from the type signature (`getGUID()` is documented `@platform darwin,win32` only). **Adopted fix (owner's own call, accepting the trade-off):** the tray is no longer destroyed when "Run in background" is turned off mid-session — only at real app quit (`will-quit`) or a `deleteAllData` reset (a genuinely new boot() generation, where stale closures are the actual concern). `backgroundModeEnabled` still fully governs whether closing the window quits or hides, so the setting still does what it says for that behavior; the one accepted regression is that an already-shown tray icon no longer disappears the instant the toggle goes off — it lingers until Chronicle actually quits. Settings' note text was updated to say so plainly. **Revised again same day — new setting, startMinimized (owner's request):** "Start minimized to tray" — only takes effect when autoStart and backgroundMode are both also on (an autostart launch with no tray to fall back to would leave a fully unreachable, windowless process); a manual launch always shows the window regardless. Detecting *why* a given launch happened turned out genuinely platform-split, found while checking Electron's own type declarations rather than assumed: **macOS** reports it natively (`app.getLoginItemSettings().wasOpenedAtLogin`, no custom argument needed) — its `openAsHidden`/`wasOpenedAsHidden` pair exists but is deprecated and explicitly documented as not working on macOS 13+, so it's read-only detection here, never used to suppress the window. **Windows** has no equivalent per-launch signal, so `applyAutoStart()` bakes a `--hidden` flag into the login item's own `args` (Electron's `Settings.path`/`args` are `@platform win32`-only — do not exist for `darwin` at all) and `wasLaunchedViaAutostart()` reads it back from `process.argv`. **Linux** has no Electron-level login-item API regardless (per the original pass's own note), so the same `--hidden` flag doubles as its detection too, appended to the hand-written `.desktop` entry's `Exec=` line. The flag is always included whenever autostart is enabled at all (not conditionally on the current `startMinimized` value), so toggling `startMinimized` alone — without retoggling `autoStart` — still takes effect on the next login; whether to actually skip the window is decided at boot from the live settings, not from what happened to be baked into the launch arguments. Guards against firing on a `deleteAllData` reset's re-`boot()` (window already open, `process.argv` unchanged) via a `hasBootedBefore` flag limiting it to the real launch. **Also fixed same day, found by checking rather than assuming:** `process.execPath` alone is only correct for a packaged app — running from source (`electron-vite dev`) it's the bare Electron binary with no app to load at all (fixed by appending the project entry point, `process.argv[1]`, as an argument in dev); and an AppImage's `process.execPath` resolves *inside its own temporary SquashFS mount*, torn down the moment that run exits — writing that into the autostart entry would silently break on the very next login despite working during the session that enabled it, so `$APPIMAGE` (the runtime's own stable path to the actual `.AppImage` file) is used instead whenever present.
