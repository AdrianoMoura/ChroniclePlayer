# Decision Log

The authoritative status of every design decision. Specs reference these IDs inline.

Statuses: **Final** (decided; changing it requires a superseding entry) ·
**Pending** (alternatives + recommendation documented; not confirmed by the product
owner) · **Superseded**.

Rationales live in the linked specs; this log is the index and the status of record.
When a Pending decision is confirmed, update its status here **and** remove the Pending
labels at its spec references, in the same change.

| D-032 | **Scope policy: minimal at start, incremental by feature.** Initial auth requests `youtube.readonly` only. Comment `likeCount` is shown read-only; there is no like button on a comment. **Revised 2026-07-13 (`bugs.md` B-067):** the first four incremental-consent call sites (like, subscribe, post comment, reply) originally opened the system browser for Google's consent screen the instant a write action was attempted, with no in-app warning — jarring, since the user had no reason to expect their click to pop open a browser tab. Separately: reading comments (`commentThreads.list`) turns out to also require the write scope in practice, not just readonly as this decision originally assumed — confirmed by the owner's live testing (granting the scope via Like is what makes comment-reading start working). | D-045 | **Embedded-player session = Electron's ordinary unnamed default session (no custom `webPreferences.partition` anywhere), shared by the main window (and therefore the player's plain `<iframe>`, which always inherits its embedding page's session) and a new "Sign in to YouTube" action** (`bugs.md` [[B-093]]) — chosen over per-cookie injection between two separate sessions. | D-046 | **Miniplayer continuity (`bugs.md` [[B-045]]): docking to the corner keeps the exact same live `<iframe>` instance mounted (no restart); extracting to an always-on-top window cannot, and hands off a playback snapshot to a fresh instance there instead.** Two different answers for what looked like one question, because they're not the same technical problem. Extracting opens a second `BrowserWindow` (`alwaysOnTop: true`) — a genuinely different renderer process, so the DOM node itself cannot move there — loading the exact same renderer bundle with an `?extract=<videoId>&t=<seconds>&autoplay=<0|1>` query string that `main.tsx` checks to render a bare, chrome-less `ExtractedPlayerWindow` instead of the full app; the main window's player then closes outright, since playback now lives in that window. Docking stays within the same renderer process, so the same live iframe *should* be able to keep running — **first attempt got this wrong**: it used a React portal to move the iframe between a full-view slot and a corner-box slot, which shipped and immediately restarted the video on every dock in the owner's live test, because moving an `<iframe>` to a different DOM parent (exactly what a portal does, even without detaching it from the document) makes Chromium reload it — a browser behavior, not a React bug, not fixable by portaling "more carefully." **Revised same day**: dropped the portal; `PlayerSurface` now renders at one permanently stable tree position and never moves in the DOM at all, instead measuring whichever slot placeholder (`ResizeObserver`-watched, in a non-scrolling region so scroll ticks don't need tracking) the active layout (`PlayerDetails` or `MiniPlayerBar`, both still always-mounted, CSS-hidden when inactive) provides, and mirroring that rect via `position: fixed` inline styles. Also added, per the owner's same live-test feedback: the corner box is resizable (native `resize: horizontal`, default width raised from 260px to 360px) and the explicit "Miniplayer" button was removed — the owner's actual ask was automatic-only docking on leaving a playing video, and the manual button read as redundant clutter once that automatic path worked. Per the product owner: both docking and extraction legs landed in the same pass, accepting the reload for the extract leg as an inherent limitation of crossing a process boundary, not something to keep chasing a workaround for. **Revised again same day, third round**: the next live test found docking didn't fire via *any* path — root causes were (a) every "hard" navigation-away action (sidebar clicks, search submit, account switch) called `setPlayerStack([])` directly, never consulting the dock decision at all, fixed with a shared `leavePlayerForNavigation()` that collapses the stack to the current video and docks it if still going; and (b) the dock decision itself was gated on the IFrame API's literal `PLAYING` state, which depends on an `onStateChange` round trip not reliable enough to gate a core feature on — loosened to "still going" (true unless explicitly paused or ended), exposed as `PlayerSurfaceHandle.isStillGoing()`. **Revised again same day, fourth round**: the next live test surfaced six more gaps, all fixed in this pass. Extraction gained a return path — closing the always-on-top window now broadcasts `player:restoreFromExtract`, which re-opens that video docked in the main window — and reliable autoplay, by having `ExtractedPlayerWindow` speak the same postMessage widget protocol as the main player (`enablejsapi=1`, explicit `command('playVideo')` after handshake, `autoplayPolicy: 'no-user-gesture-required'`) instead of trusting the embed's own `autoplay=1` alone under Electron's stricter top-level-navigation policy; the same protocol's `infoDelivery` messages are what let the restore resume close to the actual playback position (persisted via `beforeunload` → `setResumePosition`). The extract window (and, once noticed, the B-093 sign-in window) now also calls `removeMenu()` — neither should show Electron's native menu bar. The resize handle moved from native CSS `resize: horizontal` (which anchors its own grab handle to the box's bottom-right corner — exactly where the whole box already sits against the screen's corner, making it awkward to grab) to a custom top-left drag handle, with the resulting width persisted as `miniplayerWidth` in settings rather than resetting every launch. And a real navigation-stack bug was fixed: opening a video from any *fresh browsing* action (feed, search, priority/channel-preview sections, URL prompt) now explicitly replaces the stack instead of defaulting to push mode, so docking one video and then opening an unrelated one no longer buries the first one for Back to surface later — push mode is now reserved for the one case it's actually meant for, opening a video via an in-description link while watching another. **Revised again same day, fifth round**: the fourth round's own resize-handle and extract-autoplay fixes turned out not to work either, both for reasons specific to how those fixes were built rather than the underlying ideas being wrong. The resize handle was positioned `absolute; top: 0; left: 0` *inside* `.miniplayer` (z-index 20) — but the video itself is a separate always-mounted element (`.player-stage`) mirroring the stage slot's rect at z-index 21, one layer above, painted directly over that same corner: no z-index tweak on the handle could win, since a child can never paint above a sibling stacking context with a higher z-index than its own parent's. Fixed by giving the handle real layout instead — `.miniplayer` is now a flex row of a fixed-width left-edge strip plus a `.miniplayer-content` column holding the video slot and title bar, so the mirrored iframe (which only ever covers the stage slot's own rect, now inset by the strip) structurally cannot overlap the handle. Separately, the extract window's autoplay fix from last round was correct but never actually exercised: `extractToWindow` hands the extract window a `playing` flag read from `PlayerSurface`'s `getPlaybackSnapshot()`, which used the exact same overly strict `playerStateRef.current === 1` check that round three of this same decision already found and loosened for the *docking* decision (`isStillGoing()`) — `getPlaybackSnapshot` had simply never been updated to match, so it kept handing off `playing: false` whenever the autoplay-initiated `onStateChange` round trip hadn't landed yet, and the extract window's autoplay logic was faithfully honoring that (correct) instruction. Fixed by having `getPlaybackSnapshot().playing` reuse `isStillGoing()` too. **Revised again same day, sixth round**: the owner found D-038's default playback speed wasn't reaching the extracted window at all — it always opened at 1x. Root cause: `extractPlayer` never had a `defaultPlaybackRate` parameter in its IPC signature, so there was no path for the setting to travel through at all (unlike the main player, which gets it as a normal prop from `App.tsx`'s `settings` state) — not a bug in the widget-protocol plumbing itself, just a parameter that was never added when `extractPlayer` was first written. | D-047 | **On an account's very first sync, every discovered video is marked read on arrival — not just the backlog published before today** (`bugs.md` [[B-105]]) — supersedes the original B-020/B-069 rule, which only auto-read backlog videos and left same-day videos unread. **Superseding rationale (the product owner's own call, 2026-07-16):** a first sync has no prior visit to judge "new since you were last here" against — every video it discovers, today's included, is an equally uninformed guess about relevance, so assuming any of it is unread-worthy is an unjustified assumption, not a real signal. | D-048 | **Removed the "channel unavailable" state entirely — an RSS 404 is just an ordinary per-channel failure now (retried next cycle), never a permanent, un-retried "channel deleted" verdict** (`bugs.md` [[B-110]]) — supersedes `youtube-api.md`'s original "Channel deleted/terminated" failure-handling row (mark `unavailable`, stop polling, show in a settings list). That row was never an actual product decision — it was an assumption baked in during earlier development with no owner sign-off and no corresponding `decisions.md` entry, surfaced now because it caused a real, silent bug: a single transient RSS 404 (YouTube's RSS edge can 404 for reasons that have nothing to do with the channel actually being gone) permanently excluded a channel from `listSubscribedChannels` — and therefore from every future routine sync **and** from the on-demand scroll-triggered archive backfill, since both read from the same query — with no retry, and no self-healing path, since the very query that would have reset the flag on a later successful check never ran again once excluded. The promised "settings list" surfacing this state was also never built, so the whole thing was invisible: a channel just silently stopped updating forever. **Superseding rationale (the product owner's own framing, 2026-07-16):** Chronicle's experience should work like YouTube's own pagination/discovery — keep trying to fetch content until a result genuinely comes back empty, that's how you know you've reached the end; a single failed attempt is never proof of anything permanent, and RSS calls cost no quota, so there's no efficiency reason to ever stop asking. **Exercised 2026-07-16:** the `'channel-unavailable'` domain error kind, `channelUnavailable()`, `markChannelUnavailable()`, and the `available` column/filter (`channels.available`, migrated away in schema v8) are all removed outright rather than left dormant; `rss-client.ts`'s 404 branch now falls through to the same `internal(...)` failure every other non-2xx RSS response already threw, which `discoverChannel`'s existing generic per-channel failure handling (log + retry next cycle) already covered before this change — no new retry mechanism was needed, only removing the special case that pre-empted it. | `youtube-api.md` |
| D-049 | **Ordinary per-cycle RSS sync failures no longer show a banner — only a systemic failure does (every polled channel failing at once, on a poll wide enough that random noise couldn't explain it)** (`bugs.md` [[B-110]]) — supersedes the original behavior, which showed a "{count} channel(s) failed" banner (with expandable per-channel details) any time `SyncReport.outcome === 'partial'`, i.e. any cycle with at least one failed and one succeeded channel. Once [[D-048]]'s live investigation confirmed YouTube's own RSS backend routinely returns transient 404/500 for genuinely active channels — independent of Chronicle, non-deterministic (the same channel can fail one cycle and succeed the next) — it became clear `outcome: 'partial'` would be true on essentially *every* cycle forever (never converging to zero, since it's a rolling noise floor across ~230 channels each queried independently), making the banner a permanent fixture the owner could never act on or dismiss for good — exactly the kind of "something on screen nobody put there for a reason" the calm/predictable-UI principle (`CLAUDE.md`) argues against, and worse, training the owner to stop reading sync banners at all (alarm fatigue), which would blunt a *real* failure signal too. **Rationale (the product owner's own call, 2026-07-16):** stop surfacing per-cycle partial failures entirely — they're retried automatically next cycle regardless (D-048) — and reserve the banner for a signal actually worth the owner's attention: every polled channel failing in the same cycle (`outcome === 'failed'`, gated on `channelsPolled > 1` so a single unlucky manual per-channel refresh, [[B-036]], can't trip it from ordinary noise alone) — a pattern random per-channel RSS flakiness essentially cannot produce on its own, so it's a reliable proxy for a real problem (e.g. the user's own network being down). **Exercised 2026-07-16:** `App.tsx`'s `refresh:done` handler now checks `outcome === 'failed' && channelsPolled > 1` instead of `outcome === 'partial'`; the old `app.banner.refreshPartial` string is replaced by `app.banner.refreshAllFailed`. Ordinary partial failures still get logged (`sync_log`, `SyncReport.failures`) for anyone who goes looking — they're just not pushed at the owner as a banner anymore. | `youtube-api.md` |
