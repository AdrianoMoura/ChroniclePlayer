### B-086 — Members-only videos never show up in the feed
- **Type:** bug · **Severity:** major
- **Status:** Resolved (research thread closed) · **Reported:** 2026-07-15 · **Target:** 0.4.9
- **Area:** sync
- **What happens:** a video restricted to channel members doesn't appear in
  Chronicle's list at all, even for the owner's own membership on that channel.
- **Expected:** at minimum, members-only videos should be discoverable/listed like any
  other video from a subscribed channel — no special handling needed once discovered
  (per the owner: even if playback turns out not to work, just knowing the video exists
  is the ask).
- **Code refs:** `src/adapters/rss/rss-client.ts` (`parseFeed` — structurally can't
  carry members-only content, unauthenticated); `src/adapters/youtube/api-client.ts`
  (`listUploads` — `playlistItems.list` on the uploads playlist, called with the
  signed-in user's own OAuth token, no client-side filtering by privacy/visibility);
  `src/core/sync-service.ts` (`discoverChannel`'s gap-backfill, `backfillArchive` —
  both page through `listUploads`).
- **Resolved:** 2026-07-20 · **Commit:** n/a (research/spec change, no code change) ·
  **Outcome:** Won't fix
- **Resolution:** confirmed RSS can never carry this (unauthenticated, no way for it to
  know who's asking). The remaining open question — whether the *authenticated* path
  (`playlistItems.list` via `listUploads`, already used by both gap-backfill and
  on-demand archive backfill) can see members-only uploads when called with a genuine
  member's own OAuth token — was tested directly with the owner's explicit
  authorization: a one-off diagnostic reused the app's own already-stored OAuth
  credentials (the existing refresh token, no new consent flow) to mint an access
  token exactly the way `GoogleAuthProvider` does, then called `playlistItems.list`
  (part=snippet,contentDetails, 3 pages/60 items) on a channel's uploads playlist where
  a members-only video was known to have posted ~1h earlier. Every item came back
  already known — the members-only upload, chronologically sitting between two known
  public videos, was not in the response at all. This confirms the uploads playlist an
  authenticated call reads from reflects the channel's **public** upload history only,
  not a per-viewer view filtered by the caller's own membership. Within the YouTube
  Data API v3's documented, TOS-compliant surface (no Innertube/undocumented
  endpoints, `youtube-api.md` §Terms-of-service constraints), there is currently no way
  to identify members-only videos reliably — a genuine data-source limitation, not a
  gating bug in `possibleGap`/`backfillGap`. Closed as Won't fix for now; revisit if a
  different, official solution ever surfaces.
